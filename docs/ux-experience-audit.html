00 — Before the critique

What's fair game here, and what isn't

apps/web/package.json says, in its own words: "Bare-bones UI; design comes later." globals.css opens with "Deliberately minimal — functionality over polish this pass." That's not a discovery — it's the stated plan, and treating "it looks plain" as a finding would be reviewing a foundation as if it were a finished house.

What follows instead is aimed at what a visual pass won't fix on its own: missing information in the core interaction, sequencing that confuses a first-time user regardless of paint, and copy that leaks internal implementation detail to real people. Those are flagged P0/P1. Genuine polish items are included too, tagged P2/P3 — they're just not what's holding the score down.

01 — Ranked

The problems that would actually make someone leave

Ranked by how directly each one blocks a first-time user from getting to the product's actual value.

P0

The core interaction shows no content to judge

The whole product is "watch two pieces of content, pick the better one." The live vote deck renders that as two bare labels — nothing else:

as rendered, apps/web/src/components/VoteDeck.tsx:84–89Submission a3f9c210 Submission 7e1bb402

No video, thumbnail, caption, or creator name. This isn't a styling miss — the Deck/Pair API contract only ever returns submission IDs (apps/web/src/lib/types.ts:84-97), so there's nothing to render even if a <video> tag were added today. Same gap in the final public vote. This is the highest-leverage fix in the app — little else matters until it's fixed.

P0

Money-critical screens read as a jargon dump

The moment a brand is about to fund a challenge — peak trust-sensitivity — they see, unexplained: Pool, Stipend pool, Round-2 survivor bonus pool, Crowd favourite, Take rate. Then a "Confirm funding" step crams four dollar figures into one run-on sentence. Nothing explains what escrow means before a Stripe form appears.

P1

Rally links are raw database IDs

/v/cmsi2tx040000kqw8kvlgcm1g — the entire growth loop's shareable unit is a 25-character CUID. Nobody puts that in a TikTok bio. The mechanic underneath (stable per-creator link, rally XP, two-currency split) is well designed; it's undercut by the one thing that has to be typeable and shareable being neither.

P1

Every empty state is one grey line with no next step

"No challenges yet." / "No payouts yet." / "No rounds opened yet." / "No finalists yet." / "No active campaigns right now." — five screens, same pattern: state the absence, offer nothing. None say why, or what to do about it.

P2

Gamification with no visible rules

Tier badge, taste score, streak — all bare labels, zero explanation of what they mean or how to progress. The existing design mockups (screen 20) explicitly call tiers "functional not cosmetic" — the shipped version is a static pill.

It's an honest, well-built seeded identicon per the code comments — but the user-facing copy calls it "AI-generated," which is a small credibility ding the moment someone looks closely, on a product where creator identity is the whole point.

04 — Retention

The habit loop is built. It isn't felt.

Streaks, tiers, rally XP, and taste score are all real, working server-side systems (streak.service.ts, tier.ts, RallyStats). None of them produce an on-screen moment today — no toast, no animation, no "+1 day." A number changes in the database; nothing on screen tells the user it changed, or that it mattered.

05 — The best news in this report

This has already been designed once

docs/moment-prototype.html is a real, wired 37-screen mockup — a warm-paper surface, a restrained accent-blue, semantic color for money and status, real iconography. Nine companion docs/mockup-*.html files break it down screen by screen with an explicit rationale for every mechanic. None of it made it into apps/web.

docs/mockup-09-round1-teaser-peer-vote.html

Already designed: thumbnail cards with play-icon overlays, a "vote 3 more to unlock your result" progress bar, and "You won't see who made these" reassurance copy — solving the exact P0 vote-deck problem above, on paper, before this build even started.

That changes the scope of the recommendation for almost everything in this report from "design something new" to "wire the frontend to the design that already exists." A materially smaller lift — and the starting point should be that folder, not a blank canvas.

06 — Mobile

What's right, what's missing

Already correct: the 480px breakpoint stacks the vote-pair layout vertically and grows every button to a 48–52px touch target — a real, deliberate pass, done properly at the CSS layer.

Missing: a mobile-specific navigation pattern — the same top bar ships at every width, where a bottom tab bar fits this five-screen core loop far better, and is the pattern every reference app in this category uses for exactly this reason. Sharing the rally link only calls navigator.clipboard.writeText, with no navigator.share() fallback — for a growth mechanic that depends entirely on sharing, that's the difference between one tap into the native share sheet and "copy a link, then go find somewhere to paste it." Every async screen shows literal "Loading…" text rather than a skeleton state, which reads worse on mobile's higher latency sensitivity.

07 — In order

Fix these five first

  1. Give the vote deck something to show. Extend the deck/pair API to return a thumbnail, caption, and post-reveal identity per submission; render it in VoteDeck.tsx and PublicVote. Unblocks the entire core loop on its own.

  2. Replace raw CUID rally/referral codes with a short, human-typeable slug — everywhere one is generated, stored, or displayed.

  3. Give / and /login an actual first impression — one line of value prop and real branding before the phone-number ask; move the role picker ahead of phone entry.

  4. Rewrite every empty state and the leaked Mux debug string to answer what/why/next. Copy-only, low-risk, high-visibility — an afternoon of work across five-plus screens.

  5. Progressive-disclose the funding breakdown: one total number up front, the pool/stipend/take-rate itemization behind a "see breakdown" toggle, plus one plain-English line on what escrow means.

08 — Final

Overall UX score

29/ 100 — current shippable experience, not a verdict on the plan

The backend is unusually well-modeled for this stage: a two-currency vote split, honest cents-based money, a real anti-low-effort-voting mechanic, a legitimately clever growth-loop data model — and a complete visual design system already exists on disk. The gap between "engineering spine" and "shippable product" is real, but it's a wiring problem, not a from-scratch design problem, which is a materially better position than the raw number suggests in isolation.

First impression and value prop pull the floor down hardest — the P0 vote-deck gap alone caps the core-loop ceiling near zero until it's fixed. Trust and conversion sit in the middle, held back by unexplained jargon at money moments rather than anything structurally wrong. The retention primitives (streak, tier, rally) are architecturally sound and would meaningfully lift this score the moment they're given any on-screen presence at all.

Tested against a local stack — Postgres + Redis via docker compose, the NestJS API, and the Next.js client — with a dev-minted JWT standing in for phone-OTP login (Twilio isn't configured in this environment, as expected pre-launch).
